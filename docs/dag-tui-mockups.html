Outline — primary plan_detail view

Topologically ordered, indented by depth. A join step lists every dependency by short id inline. z re-roots at the cursor step (next tab). i opens the inbox with an open-count badge. Status color is the step glyph + title; the cursor is a row highlight + a yellow → (kept distinct from implementing-yellow because it's a row treatment, not a text recolor).

┌─ Plan: add-oauth-login · branch feat/oauth · 7 steps · 1 blocked 1 in review ─┐ ✓ a1f3 Scaffold auth module review ✓ root │ ├─✗ b2e7 Users + sessions schema review ✗ → spawned r8k2 │ └─● r8k2 ↳ Fix nullable session token corrects b2e7 · attempt 2 │ ├─◐ c9d4 OAuth provider client review in-flight (codex) │ └─⊘ d5a8 Login UI form BLOCKED · question → ○ e3b1 Session middleware deps: b2e7, r8k2 ○ f7c2 Wire end-to-end login flow join · deps: c9d4, d5a8, e3b1 └─ j/k move · l open · z focus · a add · D deps · i inbox(1) · ? help ──────┘

Strengths

  • No layout engine; scrolls; diff-friendly
  • Depth = indentation reads instantly
  • Color tells state at a glance across branches
  • Closest to today's list — low relearn

Notes

  • Join steps appear once; fan-in is the textual deps: list
  • ✗ b2e7 = review-failed: step is structurally complete but coloured red as the "problem" state; its fix r8k2 is the live work

Focused — re-root at a subtask (z on a step)

Re-roots the outline at the cursor step and shows only that step and its transitive dependents (downstream cone); unrelated branches hide. Breadcrumb chrome shows the focus path; Z/Esc pops back toward the true root. Pure view transform — the scheduler still spans the whole DAG. (Here: focused on b2e7.)

add-oauth-login › focus: b2e7 Z back to root ┌────────────────────────────────────────────────────────────┐ ✗ b2e7 Users + sessions schema review ✗ (focus root) └─● r8k2 ↳ Fix nullable session token corrects b2e7 · attempt 2 └─○ e3b1 Session middleware deps: b2e7, r8k2 └─○ f7c2 Wire end-to-end login flow join · deps: c9d4, d5a8, e3b1 hidden (unrelated): a1f3 · c9d4 · d5a8 └─ j/k move · l open · Z/Esc back to root · i inbox(1) · ? help ─────┘

Strengths

  • Cuts a wide plan down to the branch you care about
  • Breadcrumb keeps "where am I" obvious; cheap nesting
  • Doesn't perturb scheduling — safe to use mid-run

Locked

  • Downstream dependents cone (confirmed). Upstream context rides the breadcrumb, not the body — no second mode.
  • Hidden-count footer kept for orientation.

Interruptions inbox (View::Inbox) — run-through answering

Every open question/blocker across all branches, decoupled from DAG navigation. Submitting an answer auto-advances to the next open one so you clear the whole queue in a single pass — the actual human-in-the-loop efficiency win. Resolved items stay (dimmed) for context; other branches keep running while you work the queue.

┌─ Interruptions · add-oauth-login · 1 open · 2 resolved · run-through 1/1 ─┐ → ⊘ QUESTION step d5a8 · Login UI form · attempt 1 Which OAuth providers must launch with? The plan says "social login" but not which set. proposed: 1 Google + GitHub 2 Google only 3 Google + GitHub + Microsoft ✓ BLOCKER step c9d4 · resolved 4m ago "needs OAUTH_TEST_CLIENT_SECRET" → resolved w/ comment ✓ QUESTION step b2e7 · resolved 12m ago token column type → chose option 2 (TEXT, nullable) └─ ⏎ answer (→ next open) · r resolve blocker · Esc exit · c9d4 still running ─┘

Strengths

  • One queue for all human debt → batch the bottleneck
  • Auto-advance = answer several in a row, no list bouncing
  • Footer reassures: branches keep moving while you answer

Locked

  • Own View::Inbox (confirmed), not a plan-detail pane.
  • Run-through iterates open items; resolved shown dimmed for context.

Answer modal — ranked proposals + comment + freeform

Opened from the inbox or a blocked step. Proposed answers in priority order (agent's #1 pre-selected). Pick one and/or add a comment, or drop to freeform. Blocker variant has no options — just resolve / resolve-with-comment. Chosen answer + comment both flow into the bounded resolution injection (redesign §8).

┌───────────── Answer · step d5a8 ─────────────┐ │ Q: Which OAuth providers must launch with? │ │ │ │ ● 1 Google + GitHub agent's pick │ │ ○ 2 Google only │ │ ○ 3 Google + GitHub + Microsoft │ │ ○ f ✎ type a freeform answer… │ │ │ │ comment (optional, injected next attempt): │ │ ┌────────────────────────────────────────────┐ │ │ │ also gate Microsoft behind a feature flag │ │ │ └────────────────────────────────────────────┘ │ │ │ │ j/k pick · e edit comment · ⏎ submit · Esc cancel │ └──────────────────────────────────────────────────┘ on submit: d5a8 → waiting-for-turn; resolution + comment injected next attempt

Strengths

  • Priority order guides without forcing the human
  • Comment + chosen option both injected (bounded — §8)
  • Extends existing answer_modal.rs

Locked

  • No "let the agent decide" row — resolving a question needs an explicit answer/freeform (the agent asked because it lacked confidence). Abandoning a step is ralph skip, separate.
  • Question vs. blocker = two layouts to maintain

Rejected alternates (kept for the record)

Not building these. Swimlanes and the connector graph were evaluated; the outline won on render cost, edit ergonomics, and similarity to today's view. Recorded so the trade-off isn't relitigated later.

B · Swimlanes one column per independent branch ─ visually sells parallelism, but lane width/wrap is fiddly, breaks past ~4 lanes, and join steps belong to no lane. C · Connector graph drawn ASCII edges, true fan-in ─ best whole-plan mental model, but edge routing is a project in itself and it's poor for cursoring/editing. If a future need arises, C could return as a read-only `g` overview.
